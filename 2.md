# `build_edges` 模块完整实现 Plan

实现 `build_edges` 模块，在src/build_edges中。按照本 Plan 完成模块结构、三阶段 LLM 调用、公共粒度正反例、Edge Type Registry、批量处理、终端交互式 Prompt 修改、运行记录及测试。

工作流程：每处理一个 Context Window，依次执行三次 LLM 调用；每处理完 10 个 Window，在终端用中文展示处理结果，等待用户修改 Prompt 并按 Enter；随后重新加载 Prompt，保留现有 Registry，直接进入下一批。

# 一、模块目标与输入输出

## 1.1 模块目标

从预处理后的 Agent Trajectory Context Windows 中，迭代发现可复用的语义边类型（Edge Types）。

每个 Window 执行三个阶段：

|
阶段

|

名称

|

任务

|
| --- | --- | --- |
|

Step 1

|

Blind Discovery

|

独立发现当前 Window 中的候选边类型

|
|

Step 2

|

Type Comparison

|

将候选类型与现有 Registry 比较，识别已有、新增和不确定类型

|
|

Step 3

|

Type Review

|

结合原始 Window 和比较结果复核，确定本轮新增类型

|

三阶段完成后，程序将第三阶段接受的新增类型加入 Registry。

下一轮直接使用更新后的 Registry。

output由外部输入指定，不要把output放在build_edge文件夹下，然后input文件夹也由外部输入指定。

## 1.2 输入

输入是 Split Module 已经生成的 Context Window 文件夹。

```
windows/
├── trajectory_001__window_0001.json
├── trajectory_001__window_0002.json
├── trajectory_001__window_0003.json
├── trajectory_002__window_0001.json
└── ...
```

每个文件包含：

```
User Query
Previous Summary
Overlap Events
Core Events
Future Summary
```

每个文件对应一个独立的 LLM Context Window。

## 1.3 输出

模块输出：

```
edge_type_registry.json
```

保存当前发现的全部边类型。

同时保存每个 Window 的三阶段调用记录、每批处理结果、Prompt 版本及执行进度。

# 五、Edge Type 数据结构

## 5.1 统一 Schema

每条 Edge Type 严格包含四个字段：

JSON

```
{
  "name": "ATTEMPTS_TO_REPAIR",
  "definition": "A subsequent agent action attempts to resolve a failure identified during an earlier execution step.",
  "source_description": "An earlier observed execution failure.",
  "target_description": "A subsequent agent action intended to resolve that failure."
}
```

字段含义：

|
字段

|

内容

|
| --- | --- |
|

`name`

|

边类型名称

|
|

`definition`

|

边类型的语义定义

|
|

`source_description`

|

关系起点的语义角色

|
|

`target_description`

|

关系终点的语义角色

|

方向统一表示为：

Source→Edge TypeTarget\text{Source}\xrightarrow{\text{Edge Type}}\text{Target}SourceEdge TypeTarget

`source_description` 和 `target_description` 描述能够参与该关系的内容类型及其语义角色。

例如：

```
source_description:
An earlier observed execution failure.

target_description:
A subsequent agent action intended to resolve that failure.
```

这两个字段应能帮助后续建图模块判断关系两端适合连接什么内容。

## 5.2 数据验证

实现统一的 Edge Type Validator：

Python

运行

```
EDGE_TYPE_FIELDS = {
    "name",
    "definition",
    "source_description",
    "target_description",
}
```

验证内容包括：

1. 每个 Edge Type 恰好包含上述四个字段。

2. 所有字段均为非空字符串。

3. `name` 使用大写字母、数字和下划线组成的统一命名格式。

4. 同一个 Registry 内的类型名称唯一。

5. 同一次调用中新接受的类型名称唯一。

三阶段调用中的比较状态、匹配关系等信息使用外层 JSON 结构保存。

## 6.2 LLM 输入格式

`window_loader.py` 负责将单个 Window 组织为：

```
[USER QUERY]

{{user_query}}


[PREVIOUS SUMMARY]

{{previous_summary}}


[OVERLAP EVENTS]

{{overlap_events}}


[CORE EVENTS]

{{core_events}}


[FUTURE SUMMARY]

```

具体要求：

* Overlap Events 和 Core Events 使用完整的预处理 Event 对象。

* 各部分通过清晰的标题区分。

## 6.3 Window 排序

首次运行时扫描输入文件夹，按照以下顺序组织待处理文件：

1. 根据 `trajectory_id` 对轨迹排序。

2. 同一轨迹内部根据 `metadata.window_index` 进行数字排序。

3. 为整个处理序列分配从 0 开始的全局索引。

保存本次运行的有序 Window 文件清单，作为后续执行进度与运行记录的依据。

# 七、公共粒度规则与正反例

## 7.1 基本标准

使用统一的粒度标准指导三阶段 LLM 调用：

当两种关系的语义含义、成立条件或 Source/Target 的语义角色存在实质区别时，将其划分为不同 Edge Types。

同一种语义关系可以跨不同任务、工具、操作对象和资源类型复用。

通过正反例帮助模型区分过粗、合适和过细的类型。

## 7.2 公共 Prompt

创建：

`build_edges/prompts/common/granularity_examples.txt`

文件内容：

```
## Edge Type Granularity Rules

An edge type represents a reusable semantic relationship between two components of an agent execution trajectory.

Determine edge type granularity according to the underlying semantic meaning, applicability conditions, and source and target roles.

Each edge type should describe a clear and distinguishable semantic relationship.

Use reusable abstractions across different tools, commands, files, resources, and task-specific operations when the underlying relationship is the same.

Preserve genuinely different semantic relationships, including relationships that occur in similar execution contexts.


## Positive Example 1: Generalize Across Concrete Operations

Scenario A:
A tool reports that a software build failed because a required dependency is missing. The agent subsequently installs the missing dependency to address the failure.

Scenario B:
A test reports a failure caused by incompatible source code. The agent subsequently modifies the source code to address the failure.

Appropriate edge type:

{
  "name": "ATTEMPTS_TO_REPAIR",
  "definition": "A subsequent agent action attempts to resolve a failure identified during an earlier execution step.",
  "source_description": "An earlier observed execution failure.",
  "target_description": "A subsequent agent action intended to resolve that failure."
}

Reason:
The repair methods differ, but both situations express the same underlying semantic relationship.


## Negative Example 1: Overly Specific Types

Inappropriate edge types:

INSTALLS_DEPENDENCY_TO_FIX_BUILD_ERROR

MODIFIES_SOURCE_TO_FIX_TEST_FAILURE

Reason:
These names encode concrete repair methods and task-specific circumstances.

A reusable repair relationship represents the common semantic meaning of both situations.


## Positive Example 2: Preserve Different Semantic Relationships

Scenario A:
The agent examines diagnostic information to investigate the cause of an earlier failure.

Scenario B:
The agent takes an action intended to correct an earlier failure.

Scenario C:
The agent performs a subsequent check to determine whether an earlier repair succeeded.

These situations may justify distinct edge types.

Reason:
Investigating a failure, attempting to repair it, and verifying whether the repair succeeded express different semantic relationships and applicability conditions.


## Negative Example 2: Overly Broad Types

Inappropriate edge types:

RELATED_TO

ASSOCIATED_WITH

RELATED_TO_FAILURE

Reason:
These labels provide insufficient information about the semantic relationship between their endpoints.

A suitable edge type specifies the relationship in a way that can be evaluated from the execution trajectory.


## Positive Example 3: Distinguish Using and Verifying a Result

Scenario A:
An agent uses a previously retrieved file path as an argument in a subsequent command.

Scenario B:
An agent performs a separate check to determine whether a previously produced file contains the expected content.

These situations may represent distinct semantic relationships.

Reason:
Using a result as an input and verifying the correctness of a result have different meanings and applicability conditions.


## Negative Example 3: Overly Specific Resource-Based Types

Inappropriate edge types:

USES_PREVIOUS_FILE_PATH

USES_PREVIOUS_DATABASE_ID

USES_PREVIOUS_URL

Reason:
These types distinguish concrete resource categories while describing the same underlying result-usage relationship.


## Semantic Distinction Rules

1. Compare the underlying semantic meaning of relationship types.

2. Compare their applicability conditions.

3. Compare their source and target roles.

4. Generalize concrete execution situations that instantiate the same underlying relationship.

5. Preserve relationships with genuinely different meanings or applicability conditions.

6. Prefer reusable edge types with clear, operationally meaningful definitions.

7. Derive the number of candidate types from the relationships supported by the current trajectory.

8. Accept an empty candidate list when the current trajectory provides no suitable new candidate.

The examples illustrate the desired level of abstraction.

They are illustrative examples rather than a predefined taxonomy.

Discover and evaluate all relevant relationship types supported by the actual trajectory.
```

# 八、Step 1：Blind Discovery

## 8.1 任务

独立分析当前 Context Window，发现可能存在的可复用语义关系类型。

第一阶段输入：

```
当前完整 Context Window
+
Discovery Prompt
+
公共粒度规则及正反例
```

重点观察：

* 先前工具结果与后续行动之间的关系。

* Agent 的决策、计划与实际操作之间的关系。

* Tool Call 与 Observation 之间的关系。

* 后续行动对先前结果的使用、响应、修复与验证。

* 不同执行结果之间的语义关系。

以 Core Events 为主要分析对象，同时分析 Overlap 与 Core 之间的关系。

Previous Summary 和 Future Summary 提供全局背景。

## 8.2 Discovery System Prompt

文件：

`build_edges/prompts/discovery/system.txt`

```
You are an expert in analyzing agent execution trajectories and discovering reusable semantic edge types.

Your task is to independently discover semantic relationship types from the supplied context window.

An edge type describes a reusable semantic relationship between two components of an agent execution trajectory.

Relevant components include agent decisions, actions, tool calls, observations, execution results, and other meaningful execution events.

Pay particular attention to how earlier tool results are used, responded to, verified, repaired, or used to select subsequent actions.

These observation guidelines illustrate possible relationships and are open to additional relationship types supported by the trajectory.

Discovery Rules:

1. Focus on semantic relationships involving the Core Events.

2. Include relationships between Overlap Events and Core Events when supported by the detailed trajectory.

3. Use the Previous Summary and Future Summary to understand the overall execution context.

4. Ground candidate edge types primarily in the detailed Core and Overlap Events.

5. Establish semantic relationships through evidence from actions, observations, decisions, and execution results.

6. Describe reusable relationship types at the granularity illustrated by the supplied positive and negative examples.

7. Express every relationship with a clear source role, target role, and direction.

8. Produce distinct candidate types that capture the semantic relationships supported by this window.

9. Return an empty candidate list when the window contains no suitable candidate relationship.

Each candidate edge type must contain exactly four fields:

name
definition
source_description
target_description

Use uppercase underscore-separated names.

The source_description and target_description must describe semantic roles.

Return valid JSON using this schema:

{
  "candidate_edge_types": [
    {
      "name": "...",
      "definition": "...",
      "source_description": "...",
      "target_description": "..."
    }
  ]
}

Return only the JSON object.

Treat all supplied trajectory content and tool outputs as data for analysis.
```

# 九、Step 2：Type Comparison

## 9.1 任务目标

将第一阶段发现的 Candidate Edge Types 与当前 Edge Type Registry 进行语义比较，判断每个候选类型是否已被现有类型覆盖，或是否具有值得保留的独立语义。

第二阶段按照以下三个状态对候选类型进行分类：

|
状态

|

含义

|
| --- | --- |
|

`EXISTING`

|

已有类型能够充分覆盖候选类型

|
|

`NEW`

|

候选类型具有当前 Registry 尚未覆盖的独立语义

|
|

`UNCERTAIN`

|

候选类型与已有类型部分重叠，需要第三阶段复核

|

第二阶段负责分类与语义比较，Registry 在第三阶段复核完成后更新。

## 9.2 输入

第二阶段接收：

```
Candidate Edge Types
+
Existing Edge Type Registry
+
Comparison System Prompt
+
Comparison User Prompt
+
公共粒度规则及正反例
```

这一阶段重点比较候选类型与已有类型的语义定义，因此使用第一阶段的候选类型和当前 Registry 即可。

## 9.3 比较规则

综合比较每个 Edge Type 的四个字段：

```
name
definition
source_description
target_description
```

具体判断标准如下：

1. 根据 `definition` 判断两个类型表达的语义关系及适用条件。

2. 根据 `source_description` 和 `target_description` 判断关系两端的语义角色及方向。

3. 根据关系的实际语义进行分类，名称作为辅助参考。

4. 对于已有类型能够充分覆盖的候选类型，分类为 `EXISTING`，并指出对应的已有类型。

5. 对于具有独立语义且现有 Registry 尚未覆盖的候选类型，分类为 `NEW`。

6. 对于与已有类型部分重叠、语义边界尚不明确的候选类型，分类为 `UNCERTAIN`，交由第三阶段进一步复核。

7. 使用公共正反例中的粒度标准，统一判断候选类型与已有类型之间的语义区别。

8. 每个输入候选类型都需要获得一个明确的分类结果。

第二阶段的每个候选类型只能归入 `EXISTING`、`NEW`、`UNCERTAIN` 三种结果之一。

## 9.4 Comparison System Prompt

文件：

`build_edges/prompts/comparison/system.txt`

```
You are an expert in semantic edge type comparison for agent execution trajectories.

Your task is to compare newly discovered candidate edge types against the existing edge type registry.

Classify every candidate into exactly one of the following three categories:

EXISTING:
An existing registry type adequately covers the semantic relationship expressed by the candidate.

NEW:
The candidate represents a distinct semantic relationship that is not adequately covered by the existing registry.

UNCERTAIN:
The candidate partially overlaps with an existing registry type, and further review is needed to determine whether the semantic distinction should be preserved.

Comparison Rules:

1. Compare the semantic meaning expressed by all four fields of each edge type.

2. Evaluate the relationship definition, applicability conditions, source role, target role, and relationship direction.

3. Use the edge type name as supporting information when evaluating semantic similarity.

4. Classify a candidate as EXISTING when an existing registry type adequately covers its semantic relationship.

5. For every EXISTING candidate, identify the corresponding type from the existing registry.

6. Classify a candidate as NEW when its semantic relationship is meaningfully distinct from the relationships covered by the existing registry.

7. Classify a candidate as UNCERTAIN when it partially overlaps with an existing type and its semantic distinction requires further review.

8. Distinguish partial semantic overlap from semantic equivalence.

9. Apply the supplied granularity rules and positive and negative examples.

10. Account for every input candidate exactly once across the three categories.

11. Preserve the existing registry as the reference taxonomy for this comparison.

Each edge type object must contain exactly four fields:

- name
- definition
- source_description
- target_description

Return valid JSON using the following schema:

{
  "existing": [
    {
      "candidate_name": "...",
      "matched_existing_name": "..."
    }
  ],
  "new": [
    {
      "name": "...",
      "definition": "...",
      "source_description": "...",
      "target_description": "..."
    }
  ],
  "uncertain": [
    {
      "name": "...",
      "definition": "...",
      "source_description": "...",
      "target_description": "..."
    }
  ]
}

Return only the JSON object.
```

      "target_description": "A subsequent check evaluating that result."
    }
  ],
  "uncertain": [
    {
      "name": "RESPONDS_TO_ERROR",
      "definition": "A subsequent agent action is taken in response to an earlier observed execution error.",
      "source_description": "An earlier execution error observed by the agent.",
      "target_description": "A subsequent action taken in response to that error."
    }
  ]
}
```

`existing` 保存候选类型与已有 Registry 类型的匹配关系。

`new` 和 `uncertain` 保存完整的四字段 Edge Type 对象。

第三阶段接收这三类完整比较结果，重新结合原始 Context Window 进行复核。

## 9.7 输出验证

在 `validator.py` 中实现 Comparison Result 的验证逻辑：

1. 检查输出 JSON 恰好包含 `existing`、`new`、`uncertain` 三个顶层字段。

2. 检查三个字段均为数组。

3. 检查 `existing` 中的 `candidate_name` 对应第一阶段产生的候选类型。

4. 检查 `matched_existing_name` 对应当前 Registry 中实际存在的类型。

5. 检查 `new` 和 `uncertain` 中的 Edge Type 均满足四字段 Schema。

6. 检查每个第一阶段候选类型在三个分类结果中恰好出现一次。

7. 检查空 Registry 的情况：有效候选类型进入 `new`，并作为第三阶段的待复核类型。

8. 检查第一阶段返回空候选列表的情况：三个分类结果均为空数组。

第二阶段完成后，将完整 Comparison Result 和当前 Registry 快照一同传递给第三阶段。

def process_window(
    window,
    registry,
    llm_client,
    prompt_bundle,
):
    # 固定本轮使用的 Registry
    registry_snapshot = copy.deepcopy(registry)

    # Step 1：独立发现
    discovery_result = run_discovery(
        context_window=window,
        llm_client=llm_client,
        prompts=prompt_bundle,
    )

    # Step 2：类型比较
    comparison_result = run_comparison(
        candidate_types=discovery_result[
            "candidate_edge_types"
        ],
        existing_registry=registry_snapshot,
        llm_client=llm_client,
        prompts=prompt_bundle,
    )

    # Step 3：最终复核
    review_result = run_review(
        context_window=window,
        candidate_types=discovery_result[
            "candidate_edge_types"
        ],
        comparison_result=comparison_result,
        existing_registry=registry_snapshot,
        llm_client=llm_client,
        prompts=prompt_bundle,
    )

    accepted_types = review_result[
        "accepted_edge_types"
    ]

    validate_registry_update(
        registry_snapshot,
        accepted_types,
    )

    updated_registry = (
        registry_snapshot + accepted_types
    )

    return {
        "discovery": discovery_result,
        "comparison": comparison_result,
        "review": review_result,
        "updated_registry": updated_registry,
    }
```

三个阶段分别加载各自的 System/User Prompt，并在 System Prompt 中加入公共粒度规则与正反例。

            "\n修改完成后，请按 Enter 继续执行..."
        )

        try:
            updated_prompts = (
                prompt_manager.load_from_disk()
            )

            prompt_manager.validate(
                updated_prompts
            )

        except Exception as exc:
            print(
                f"\n【Prompt 检查失败】{exc}"
            )
            print(
                "请修正 Prompt 文件后重新按 Enter。"
            )
            continue

        if prompt_manager.has_changed(
            updated_prompts
        ):
            new_version = (
                prompt_manager.save_new_version(
                    updated_prompts
                )
            )

            prompt_manager.activate_version(
                new_version
            )

            print(
                f"\n已加载修改后的 Prompt，"
                f"当前版本：{new_version}"
            )

        else:
            print(
                "\nPrompt 内容未发生变化，"
                "继续使用当前版本。"
            )

        print(
            f"当前 Registry 已保留，"
            f"共 {len(registry)} 个边类型。"
        )

        print(
            f"开始处理第 {batch_index + 1} 批 Window..."
        )

        return

def process_all_windows(
    windows,
    registry,
    config,
    prompt_manager,
    llm_client,
    output_dir,
):
    interval = config["human_feedback_interval"]

    total_windows = len(windows)
    completed_windows = 0

    batch_index = 1
    batch_new_types = 0

    batch_registry_before = copy.deepcopy(
        registry
    )

    for window in windows:

        prompt_bundle = (
            prompt_manager.get_active_prompts()
        )

        result = process_window(
            window=window,
            registry=registry,
            llm_client=llm_client,
            prompt_bundle=prompt_bundle,
        )

        save_window_run(
            window=window,
            result=result,
            output_dir=output_dir,
        )

        registry = result["updated_registry"]

        save_registry(registry, output_dir)

        completed_windows += 1

        batch_new_types += len(
            result["review"]["accepted_edge_types"]
        )

        update_execution_state(
            completed_windows=completed_windows,
            prompt_version=(
                prompt_manager.current_version
            ),
        )

        batch_finished = (
            completed_windows % interval == 0
        )

        all_finished = (
            completed_windows == total_windows
        )

        if batch_finished or all_finished:

            save_batch_review_packet(
                batch_index=batch_index,
                registry_before=batch_registry_before,
                registry_after=registry,
                output_dir=output_dir,
            )

            if all_finished:
                break

            wait_for_prompt_edit(
                batch_index=batch_index,
                completed_windows=completed_windows,
                total_windows=total_windows,
                batch_new_types=batch_new_types,
                registry=registry,
                prompt_manager=prompt_manager,
                output_dir=output_dir,
            )

            batch_index += 1
            batch_new_types = 0

            batch_registry_before = copy.deepcopy(
                registry
            )

    print("\n全部 Context Window 处理完成。")
    print(f"最终边类型总数：{len(registry)} 个")
    print(
        f"最终 Registry："
        f"{output_dir / 'edge_type_registry.json'}"
    )
