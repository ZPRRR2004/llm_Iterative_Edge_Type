# `build_edges` 增量修改 Plan：Step 3 新增 Existing Edge Type Revision

## 一、任务目标与修改范围

请在现有 `build_edges` 模块基础上，增量修改 Step 3：Type Review。

目前 Step 3 负责复核 Discovery 产生的候选类型，决定哪些候选类型应加入当前 Registry。

本次修改后，Step 3 同时承担两项职责：

1. New Type Review：复核 Step 1 发现的全部候选类型，决定接受哪些新增 Edge Type。

2. Existing Type Revision：检查 Step 2 的 `existing` 分类中，候选类型与已有 Registry 类型的匹配情况。在已有类型能够表达该候选关系、但名称或描述需要改进时，输出该已有类型的修订版本。

例如：

```
Step 1 发现：

ATTEMPTS_TO_REPAIR
  表示针对先前执行失败采取修复行动。

Step 2 判断：

ATTEMPTS_TO_REPAIR
    → EXISTING
    → REPAIRS_FAILURE

Step 3 进一步检查：

REPAIRS_FAILURE 的当前定义仅适用于 missing prerequisite。
但本轮轨迹中的修复行为针对的是代码错误。

Step 3 判断两者属于相同的底层修复关系，
因此修订已有类型 REPAIRS_FAILURE 的定义，
使其能够表达更一般的失败修复关系。
```

最终 Step 3 可以同时返回：

```
accepted_edge_types
+
revised_existing_edge_types
```

两部分结果共同用于更新当前 Registry。

```
You are an expert in reviewing semantic edge types discovered from agent execution trajectories.

A candidate classified as EXISTING may represent a genuinely distinct relationship.

5. Apply the supplied granularity rules and positive and negative examples.

9. Ensure that the relationship direction is consistent across the definition, source_description, and target_description.

10. Return valid and genuinely new relationship types in accepted_edge_types.

A candidate previously classified as EXISTING can be accepted as a new type when its underlying relationship is genuinely distinct from the matched existing type.

When an existing Registry type adequately covers a candidate, represent the candidate's relationship through that existing type.

When a candidate lacks sufficient trajectory evidence or does not represent a suitable independent relationship, omit it from accepted_edge_types.

Every accepted type must be based on a relationship represented by the original candidate set and supported by the current Context Window.

Return an empty accepted_edge_types array when no suitable new relationship types are identified.

Review every entry in the EXISTING category of the previous Type Comparison.

For each EXISTING entry:

1. Locate the complete original candidate Edge Type using candidate_name.

2. Locate the complete matched existing Registry Edge Type using matched_existing_name.

3. Compare their semantic meanings, applicability conditions, source roles, target roles, and relationship directions.

4. Examine the current Context Window to understand the specific relationship represented by the candidate.

7. Preserve the matched existing type unchanged when its current four-field definition is already appropriate.

8. Produce a revision when the matched existing type represents the same underlying semantic relationship but its current name, definition, granularity, source_description, or target_description needs improvement.

9. Preserve the original semantic identity of the existing type when revising it.

13. Apply the shared granularity rules and positive and negative examples when determining the appropriate level of abstraction.

14. Ensure that every revised type has consistent relationship direction across its definition, source_description, and target_description.

15. Return a revision only when the existing type's four-field definition needs improvement.

- name
- definition
- source_description
- target_description

Case 2: The candidate is adequately covered by the matched existing type, but the existing type's name, definition, granularity, or endpoint descriptions can be improved.

Produce a revised version of the existing type.

Case 3: The candidate represents a genuinely distinct relationship that the matched existing type does not adequately cover.

Consider accepting the candidate as a new Edge Type through Task A.

Preserve the existing type's original semantic identity.

When a revised existing type and an accepted new type are both returned, ensure that they represent genuinely distinct semantic relationships.

When several candidates are covered by the same existing type, use them together to assess whether that existing type needs a unified revision.

Define relationship types according to their underlying semantic mechanisms.

Maintain a consistent level of abstraction across the Registry.

Different concrete tools, commands, file types, resource names, error messages, or task-specific situations may instantiate the same semantic relationship.

Preserve separate types when their semantic meanings, applicability conditions, source roles, target roles, or relationship directions are genuinely different.

For example, investigating a failure, attempting to repair a failure, and verifying the outcome of a repair can represent distinct relationships.

A relationship type must remain specific enough for a later graph construction system to determine whether the relationship holds between two trajectory elements.

When revising an existing type, balance generality with clear applicability conditions and identifiable endpoint roles.
```

# Part 5：修改 Registry 更新逻辑

**需要修改的位置：**现有 Step 3 完成后，将 `accepted_edge_types` 写入 Registry 的函数。

修改后，该函数需要同时应用：

```
revised_existing_edge_types
+
accepted_edge_types
```

## 5.1 更新原则

使用当前 Window 开始时的 Registry 快照作为更新基础。

按照以下顺序构造新的 Registry：

1. 根据 `original_name` 定位需要修订的已有类型。

2. 使用 `revised_edge_type` 替换对应的已有类型。

3. 保留其余已有类型的原始四字段内容。

4. 将 `accepted_edge_types` 追加到 Registry。

5. 验证最终 Registry。

6. 验证成功后，保存并激活更新后的 Registry。

新增与修订在同一次 Registry 更新中生效。

## 5.2 参考实现

将现有 Registry 更新函数扩展为类似结构：

Python

运行

```
from copy import deepcopy


def apply_review_result(
    registry_snapshot: list[dict],
    review_result: dict,
) -> list[dict]:

    revisions = {
        item["original_name"]: item["revised_edge_type"]
        for item in review_result["revised_existing_edge_types"]
    }

    updated_registry = []

    for edge_type in registry_snapshot:
        original_name = edge_type["name"]

        if original_name in revisions:
            updated_registry.append(
                deepcopy(revisions[original_name])
            )
        else:
            updated_registry.append(
                deepcopy(edge_type)
            )

    updated_registry.extend(
        deepcopy(review_result["accepted_edge_types"])
    )

    validate_registry(updated_registry)

    return updated_registry
```

在实际调用中，先对完整 Review Result 执行 Part 4 的校验，再应用更新。

```
    context_window=context_window,

comparison_result = run_comparison(
    candidate_edge_types=discovery_result["candidate_edge_types"],
    existing_registry=registry_snapshot,
)

review_result = run_review(
    context_window=context_window,
    candidate_edge_types=discovery_result["candidate_edge_types"],
    comparison_results=comparison_result,
    existing_registry=registry_snapshot,
)

validate_review_result(
    review_result=review_result,
    candidate_edge_types=discovery_result["candidate_edge_types"],
    comparison_result=comparison_result,
    registry_snapshot=registry_snapshot,
)

updated_registry = apply_review_result(
    registry_snapshot=registry_snapshot,
    review_result=review_result,
)

registry = updated_registry

save_registry(registry)
```

以上为执行逻辑示意。具体函数名、参数和存储方式与现有项目代码保持一致。

下一 Window 的 Comparison 和 Review 使用更新后的 Registry。
