# Split Module 完整设计与实现 Plan

## 1. 模块目标

本模块负责将一个文件夹中的预处理 Agent Trajectory JSON 批量切分为多个 Window，并为每个 Window 生成前后文摘要。

输入： 一个包含多条预处理轨迹的文件夹，每个 JSON 文件对应一条完整轨迹。

输出： 一个包含全部 Window 的文件夹，每个 JSON 文件对应一次独立的下游 LLM 输入。

每个 Window 都包含以下五部分：

Wi=\(Q, Siprev, Oi, Ci, Sifuture\)W_i= \left\( Q,\\ S\_i^{prev},\\ O\_i,\\ C\_i,\\ S\_i^{future} \\right\)Wi=\(Q, Siprev​, Oi​, Ci​, Sifuture​\)

|
组成部分

|

内容

|
| --- | --- |
|

User Query

|

原始用户任务描述，包括title和text

|
|

Previous Summary

|

用一句话总结当前窗口之前的执行情况

|
|

Overlap Events

|

上一个窗口末尾的部分完整 Event

|
|

Core Events

|

本轮新加入、需要重点分析的轨迹

|
|

Future Summary

|

用一句话总结当前窗口之后的执行情况

|

整个模块只负责轨迹切分、摘要生成及输出组织。它不负责 Edge Type Discovery、实际连边、关系类型库维护或人工 Feedback。

### 1.1 整体处理流程

Input Directory

预处理轨迹合集

trajectory_001.json、trajectory_002.json、……

Trajectory Splitter

按最大 Token 数和最大 Event 数切分 Core，添加 Overlap

Summary Generator

分别调用前文与后文摘要 Prompt，生成两份一句话摘要

Window Builder

组合 User Query、Previous Summary、Overlap、Core、Future Summary

Output Directory

每个 Window 独立保存为 JSON

trajectory_001__window_0001.json、trajectory_001__window_0002.json、……

模块的执行顺序为：

1. 遍历输入文件夹，读取每一条完整轨迹。

2. 根据 Config 对当前轨迹进行确定性切分。

3. 为每个 Window 确定 Previous 和 Future 的轨迹范围。

4. 分别调用摘要 LLM 生成前后文摘要。

5. 将每个 Window 独立保存至输出文件夹。

6. 处理下一条轨迹，直至整个输入文件夹处理完毕。

不同轨迹分别处理，不允许产生跨轨迹的 Overlap。

### 4.1 输入处理规则

`query.title` 和 `query.text` 共同构成 User Query，原样保留到每个输出 Window。

`events[]` 是切分的基本序列。使用其原始数组顺序，保留全部 Event 的内容，包括 `event_id`、`step_id`、`thought`、`tool_calls` 和 `observation`。

每个预处理后的 Execution Event 都是不可拆分的基本单位。

Split 模块不对 Event 再进行总结、压缩、截断或内部拆分。这个规则同时适用于 Core 和 Overlap。

### 4.2 输入检查

读取每个 JSON 时，至少进行以下检查：

* 顶层必须存在 `query` 和 `events`，其中 `events` 必须为数组。

* 每个 Event 必须包含有效的 `event_id`，同一条轨迹中不能出现重复 ID。

* Event 按文件中的原始顺序处理，不根据时间戳重新排序。

* 空的 `events` 数组不产生 Window，记录对应文件并继续处理其他轨迹。

* 读取失败或格式不合法的文件应报告明确错误，不生成伪造的 Window。

轨迹 ID 默认使用输入文件名去掉 `.json` 后的名称。原始文件路径保存在输出元数据中，便于后续定位。


## 5. Trajectory Splitter 设计

### 5.1 基本切分逻辑

设当前轨迹包含 nnn 个完整 Events：

T=\(E1,E2,…,En\)T=\(E\_1,E\_2,\\ldots,E\_n\)T=\(E1​,E2​,…,En​\)

Splitter 将其依次划分为多个 Core：

C1,C2,…,CmC_1,C_2,\ldots,C_mC1,C2,…,Cm

每个 Core 由连续的完整 Events 构成。

正常情况下满足：

1≤∣Ci∣≤Nmax⁡1\leq |C_i|\leq N_{\max}1≤∣Ci∣≤Nmax

Tokens⁡(Ci)≤Tmax⁡\operatorname{Tokens}(C_i)\leq T_{\max}Tokens(Ci)≤Tmax

其中：

Nmax⁡=max_window_eventsN_{\max}=\text{max\_window\_events}Nmax=max_window_events

Tmax⁡=max_window_tokensT_{\max}=\text{max\_window\_tokens}Tmax=max_window_tokens

采用 Greedy Splitting（贪心切分）。

每次从第一个尚未处理的 Event 开始，依次尝试加入后续 Event。加入下一个 Event 会超过 Token 上限或 Event 数量上限时，结束当前 Core，并从下一个尚未处理的 Event 创建新的 Core。

每个 Core 至少包含一个完整 Event。

### 5.2 单个 Event 超长的处理


当单个 Event 的 Token 数已经超过上限时，直接将该 Event 作为一个独立 Core，允许突破 `max_window_tokens`。

例如：

```
max_window_tokens = 6000
max_window_events = 5
```

轨迹包含：

|

| --- | --- |

由于 Core 为空时始终允许加入第一个 Event，因此不会出现空 Core，也不会因为超长 Event 而导致循环无法推进。

### 5.3 Overlap 的计算

完成 Core 切分后，为每个 Core 添加相应的 Overlap。

假设：

YAML

```
overlap_events: 1
```

原始轨迹切分为：

```
Core 1: E1–E3
Core 2: E4–E6
Core 3: E7–E9
Core 4: E10–E13
```

添加 Overlap 后：

Window 1

Core：E1–E3

Overlap：无

Window 2

Overlap：E3

Core：E4–E6

Window 3

Overlap：E6

Core：E7–E9

Window 4

Overlap：E9

Core：E10–E13

具体规则：

* 第一个 Window 的 Overlap 为空。

* 后续 Window 向前选取最近的 `overlap_events` 个完整 Events。

* Overlap 不占用 Core 的 Event 数或 Token 预算。

* Overlap 不改变 Core 的起止位置。

* 所有 Event 都必须作为 Core 出现一次，允许作为 Overlap 额外重复出现。

* 不同轨迹之间不设置 Overlap。

如果 `overlap_events: 0`，所有 Window 的 Overlap 均为空。

即使某个重叠 Event 本身超过 6,000 tokens，也完整保留。最终输入可能超过下游模型的上下文限制，Splitter 应记录实际长度，并由模型调用方进行容量检查。

### 5.4 Previous / Future 的范围

先确定 Core 和 Overlap，再计算前后摘要对应的原始轨迹范围。

假设当前 Window：

```
Overlap: E6
Core:    E7–E9
```

则：

```
Previous Events:
    E1–E5

Overlap Events:
    E6

Core Events:
    E7–E9

Future Events:
    E10–En
```

使用 Python 数组下标表示，设：

* `core_start`：Core 起点，包含该下标。

* `core_end`：Core 终点，不包含该下标。

* `overlap_start`：Overlap 起点。

那么：

Python

运行

```
previous_events = events[:overlap_start]

overlap_events = events[overlap_start:core_start]

core_events = events[core_start:core_end]

future_events = events[core_end:]
```

这四个区间在单个 Window 中没有重叠，且按原始执行顺序覆盖完整轨迹。

Previous Summary 总结 Overlap 之前的全部历史。

Future Summary 总结 Core 之后的全部执行过程。

6. Token Counter 设计

token_counter.py 负责提供统一的 Token 数量估算接口。

max_window_tokens 约束的是完整 Core 序列化后的估算 Token 数量。本模块直接根据字符数估算，无须调用 tokenizer。

6.1 统一序列化格式与 Token 估算

建议采用紧凑 JSON，并统一使用相同的序列化函数：

import json
import math


def serialize_events(events: list[dict]) -> str:
    return json.dumps(
        events,
        ensure_ascii=False,
        separators=(",", ":")
    )


def count_core_tokens(events: list[dict]) -> int:
    text = serialize_events(events)
    return math.ceil(len(text) / 4)

这里采用固定换算比例：约 4 个字符估算为 1 个 Token。

该方法仅用于控制窗口切分长度，不能保证估算值与下游 LLM 实际使用的 Token 数完全一致。对于包含大量中文、代码或特殊符号的轨迹，估算误差可能较大。

6.2 为什么建议计算整个 Core？

为保证窗口切分和最终输出使用一致的文本表示，应当先将整个 Core 序列化，再计算其字符数。

因此，在准备添加下一个 Event 时，直接计算：

candidate_core = core + [next_event]
candidate_tokens = count_core_tokens(candidate_core)

使用 candidate_tokens 判断加入下一个 Event 后是否超过 max_window_tokens。

这样可以将 JSON 数组中的分隔符等字符一并计入估算长度，避免分别计算 Event 后再相加产生的偏差。

6.3 超长 Event 的 Token 记录

对于单个 Event 的估算 Token 数已经超过 max_window_tokens 的情况，仍然将其完整放入一个独立 Core，不进行总结、压缩、截断或拆分。

在 Window 元数据中记录：

{
  "core_tokens": 7000,
  "oversized": true
}

其中，core_tokens 表示根据字符数计算得到的估算 Token 数；oversized 表示该 Core 因单个完整 Event 超过配置上限，属于允许的特殊情况。

Overlap 不计入 Core 的长度限制，且同样保留完整 Event 内容。

## 7. Splitter 核心算法

`splitter.py` 可以按照下面的逻辑实现。

Python

运行

```
def split_trajectory(
    events: list[dict],
    config: dict,
    count_core_tokens
) -> list[dict]:

    if not events:
        return []

    max_tokens = config["max_window_tokens"]
    max_events = config["max_window_events"]
    overlap_count = config["overlap_events"]

    windows = []

    cursor = 0
    n = len(events)

    while cursor < n:

        # 1. 当前 Core 起点
        core_start = cursor

        core = []

        # 2. 贪心填充 Core
        while cursor < n:

            next_event = events[cursor]

            # 已达到最大 Event 数
            if len(core) >= max_events:
                break

            candidate_core = core + [next_event]

            candidate_tokens = count_core_tokens(
                candidate_core
            )

            # Core 非空时，检查 Token 上限
            # 第一个 Event 无论多长都允许加入
            if core and candidate_tokens > max_tokens:
                break

            core.append(next_event)
            cursor += 1

        # Core 结束位置，exclusive
        core_end = cursor

        # 3. 计算 Overlap
        overlap_start = max(
            0,
            core_start - overlap_count
        )

        overlap = events[
            overlap_start:core_start
        ]

        # 4. 计算摘要的原始轨迹范围
        previous_events = events[:overlap_start]

        future_events = events[core_end:]

        # 5. 生成 Window 中间结构
        windows.append({
            "window_id": (
                f"window_{len(windows) + 1:04d}"
            ),

            "previous_events": previous_events,
            "overlap_events": overlap,
            "core_events": core,
            "future_events": future_events,

            "metadata": {
                "overlap_start_index": overlap_start,
                "core_start_index": core_start,
                "core_end_index": core_end,
                "core_event_count": len(core),
                "core_tokens": count_core_tokens(core),
                "oversized": (
                    len(core) == 1
                    and count_core_tokens(core) > max_tokens
                )
            }
        })

    return windows
```

这里返回的是用于后续摘要生成的中间结构。

`previous_events` 和 `future_events` 仅作为 Summary Generator 的输入，不需要作为完整事件数组保存在最终输出文件中。

当 `max_window_events` 为 5、Core 已经包含 5 个 Events 时，立即结束当前 Core。

当下一个 Event 会使 Core 超过 6,000 tokens 时，将该 Event 留给下一轮。

> The agent subsequently fixed the Python compatibility issue, reinstalled pyknotid, successfully ran the README example, passed all 18 selected tests, and completed the task.

### 8.4 摘要的特殊情况

对于第一个 Window，如果 Previous Events 为空，直接设置：

Python

运行

```
previous_summary = ""
```

跳过前文摘要调用。

对于最后一个 Window，如果 Future Events 为空：

Python

运行

```
future_summary = ""
```

跳过后文摘要调用。

当一条轨迹只产生一个 Window 时，两份摘要均为空。

这些情况由代码直接判断，无须让 LLM 处理空轨迹。

### 8.5 摘要长度控制

调用摘要模型时，按照 Config 设置最大输出 Token 数。

生成后，再使用摘要模型对应的 Token Counter 检查实际长度。

如果模型输出因达到上限而中途截断，或者输出不符合一句话摘要的要求，在模块中加入retry模块，retry模块负责要求模型重新生成摘要

不通过直接裁剪字符串的方式缩短摘要。



## 9. Window Builder：最终输出格式

### 9.1 输出规则

每个输入轨迹 JSON 可以生成多个 Window。

每个 Window 独立保存为一个 JSON 文件。

例如：

```
input/
├── task_A.json
├── task_B.json
└── task_C.json

output/
├── task_A__window_0001.json
├── task_A__window_0002.json
├── task_A__window_0003.json
├── task_B__window_0001.json
├── task_B__window_0002.json
├── task_C__window_0001.json
└── ...
```

所有 Window 保存在同一个输出文件夹中，不按轨迹创建额外的子目录。

输出文件名由输入文件名和轨迹内部的窗口编号组成。

每条轨迹的窗口编号从 `0001` 开始，按执行顺序递增。

文件名不能产生冲突；输入文件名中不适合用作文件名的字符应由程序进行安全转换。

### 9.2 单个 Window 的 JSON Schema

建议使用以下结构：

JSON

```
{
  "trajectory_id": "build-cython-ext__FFaGgtD",
  "window_id": "window_0002",

  "user_query": {
    "title": "Install and fix pyknotid for NumPy 2.3.0",
    "text": "..."
  },

  "previous_summary": "The agent previously cloned the repository, inspected the environment, and fixed deprecated NumPy API usages.",

  "overlap": {
    "event_ids": [
      "event-0003"
    ],
    "events": []
  },

  "core": {
    "event_ids": [
      "event-0004",
      "event-0005",
      "event-0006"
    ],
    "events": []
  },

  "future_summary": "The agent subsequently resolved the remaining compatibility issues, reinstalled the package, and completed the required verification.",

  "metadata": {
    "source_file": "build-cython-ext__FFaGgtD.json",
    "window_index": 2,

    "overlap_start_index": 2,
    "core_start_index": 3,
    "core_end_index": 6,

    "core_event_count": 3,
    "core_tokens": 4500,
    "oversized": false
  }
}
```

上面的 Event 数组和 Token 数为格式示例。

正式输出时，`overlap.events` 和 `core.events` 必须填入对应的完整 Event JSON 对象。

实际输出示例中的 `event-0004` 应包含它原有的 Thought、所有 Tool Calls、对应的工具参数和 Observations，不能只保存 Event ID，也不能用摘要代替 Event。

每个 Window 都保存完整的 User Query 和两份摘要，因此可以单独读取并送入下游模型，无须额外加载原始轨迹文件。

### 9.4 下游 LLM 的输入方式

输出 JSON 的字段排列应保持：

```
User Query
    ↓
Previous Summary
    ↓
Overlap Events
    ↓
Core Events
    ↓
Future Summary
```

下游程序读取任意一个 Window 文件后，即可按此顺序将相应内容组织成模型输入。

`overlap` 和 `core` 必须明确区分，方便下游模型知道哪些轨迹属于此前的上下文、哪些属于当前新增内容。

Split Module 只提供这些结构化数据，不需要包含下游 Edge Type Discovery 的 System Prompt 或已有 Edge Type Registry。


## 10. 批量处理主程序设计

### 10.1 程序入口

`main.py` 接收一个输入文件夹和一个输出文件夹。

命令行：

Bash

```
python main.py --input-dir ./input --output-dir ./output
```

默认读取当前 Split 模块中的 `config.yaml`。

摘要 LLM 的模型名称、API 地址、密钥和 tokenizer 由现有的模型调用接口提供，无须增加到这份仅包含五个切分超参数的 Config 中。

### 10.2 批量处理逻辑

程序按照以下顺序执行：

```
Load Config
    ↓
Scan Input Directory
    ↓
Sort JSON Files
    ↓
For Each Trajectory:
    │
    ├── Load Trajectory JSON
    │
    ├── Validate Input
    │
    ├── Split Into Windows
    │
    └── For Each Window:
            │
            ├── Generate Previous Summary
            │
            ├── Generate Future Summary
            │
            ├── Build Window JSON
            │
            └── Save Window File
    ↓
Continue With Next Trajectory
    ↓
Finish
```

建议采用逐条轨迹处理的方式，不需要先将所有输入 JSON 全部加载到内存中。

### 10.3 `main.py` 伪代码

Python

运行

```
from pathlib import Path
import json


def process_directory(
    input_dir: str,
    output_dir: str,
    config: dict,
):

    input_path = Path(input_dir)
    output_path = Path(output_dir)

    output_path.mkdir(
        parents=True,
        exist_ok=True
    )

    trajectory_files = sorted(
        input_path.glob("*.json")
    )

    for trajectory_file in trajectory_files:

        try:
            # 1. 读取预处理轨迹
            with trajectory_file.open(
                "r",
                encoding="utf-8"
            ) as f:
                trajectory = json.load(f)

            user_query = trajectory["query"]
            events = trajectory["events"]

            # 2. 执行轨迹切分
            windows = split_trajectory(
                events=events,
                config=config,
                count_core_tokens=count_core_tokens
            )

            # 3. 逐个生成 Window
            for window in windows:

                previous_events = window[
                    "previous_events"
                ]

                future_events = window[
                    "future_events"
                ]

                # 4. 生成前文摘要
                if previous_events:
                    previous_summary = (
                        generate_previous_summary(
                            user_query=user_query,
                            previous_events=previous_events,
                            max_tokens=config[
                                "max_previous_summary_tokens"
                            ]
                        )
                    )
                else:
                    previous_summary = ""

                # 5. 生成后文摘要
                if future_events:
                    future_summary = (
                        generate_future_summary(
                            user_query=user_query,
                            future_events=future_events,
                            max_tokens=config[
                                "max_future_summary_tokens"
                            ]
                        )
                    )
                else:
                    future_summary = ""

                # 6. 组装当前 Window
                window_id = window["window_id"]

                result = build_window(
                    trajectory_id=trajectory_file.stem,
                    window_id=window_id,
                    user_query=user_query,
                    previous_summary=previous_summary,
                    overlap_events=window[
                        "overlap_events"
                    ],
                    core_events=window[
                        "core_events"
                    ],
                    future_summary=future_summary,
                    metadata={
                        **window["metadata"],
                        "source_file": trajectory_file.name,
                        "window_index": int(
                            window_id.split("_")[-1]
                        )
                    }
                )

                # 7. 每个 Window 独立保存
                output_file = output_path / (
                    f"{trajectory_file.stem}"
                    f"__{window_id}.json"
                )

                with output_file.open(
                    "w",
                    encoding="utf-8"
                ) as f:
                    json.dump(
                        result,
                        f,
                        ensure_ascii=False,
                        indent=2
                    )

        except Exception as exc:
            # 记录失败的轨迹和原因
            # 正式实现中应区分输入错误、
            # 摘要调用错误和文件写入错误
            print(
                f"Failed: {trajectory_file.name}: {exc}"
            )
            continue
```

以上代码展示主程序的执行流程，Splitter、Summary Generator 和 Window Builder 的具体实现使用前面定义的接口。
