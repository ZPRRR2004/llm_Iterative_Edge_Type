# `build_edges` 增量实现 Plan：新增 `registry_feedback` 模式

请在现有 `build_edges` 模块基础上增量实现 `registry_feedback` 人类反馈模式。保留当前已经实现的 `manual_prompt` 模式，并通过 `config.yaml` 的 `feedback_mode` 在两种模式之间切换。

`registry_feedback` 的核心流程为：

```text
每处理 10 个 Context Window
        ↓
生成 Batch Review Packet
        ↓
终端展示当前结果
        ↓
用户输入自然语言 Feedback
        ↓
Human Feedback
+ 固定 Registry Revision Prompt
+ 当前完整 Edge Type Registry
+ 公共粒度规则及正反例
        ↓
Registry Revision LLM
        ↓
为 Registry 中每个 Edge Type 指定：

KEEP
DELETE
REVISE
MERGE
        ↓
程序验证 Revision Plan
        ↓
程序应用 Revision Plan
        ↓
生成 Revised Registry
        ↓
保存完整 Revision 记录
        ↓
使用 Revised Registry 进入下一批 Window
```

本次增量实现只新增 `registry_feedback`。现有三阶段：

```text
Blind Discovery
→ Type Comparison
→ Type Review
```

保持原有执行方式。

## 4.2 多行 Feedback 输入

```python
def read_human_feedback() -> str:
    print(
        "\n请输入你对当前 Edge Type Registry 的自然语言反馈。"
    )
    print("支持输入多行内容。")
    print("输入完成后，请单独输入 END 并按 Enter。\n")

    lines = []

    while True:
        line = input("> ")

        if line.strip() == "END":
            break

        lines.append(line)

    return "\n".join(lines).strip()
```


最终得到：

# 五、四种 Revision Operation

Revision LLM 必须为**当前 Registry 中的每一个 Edge Type**指定且仅指定一种操作：

| Operation | 含义                |
| --------- | ----------------- |
| `KEEP`    | 完整保留当前类型          |
| `DELETE`  | 删除当前类型            |
| `REVISE`  | 修改当前类型的四字段定义      |
| `MERGE`   | 将当前类型合并到另一个当前已有类型 |

---

# 六、KEEP

`KEEP` 表示该类型保持完全不变。

输出：

```json
{
  "original_name": "INVESTIGATES_FAILURE_CAUSE",
  "operation": "KEEP"
}
```

应用后：

```text
Old Registry Type
        ↓
完全原样保留
        ↓
New Registry Type
```

程序使用输入 Registry 中原始四字段对象。

---

# 七、DELETE

`DELETE` 表示当前类型根据 Human Feedback 已不适合继续存在于 Registry。

输出：

```json
{
  "original_name": "REVEALS_MISSING_PREREQUISITE",
  "operation": "DELETE"
}
```

应用后，该类型不进入 Revised Registry。

删除行为及原因通过 Revision 运行记录追踪，最终 Registry 本身仍然只保存四字段 Edge Types。

---

# 八、REVISE

`REVISE` 用于调整：

```text
name
definition
source_description
target_description
```

Revision LLM 返回完整的新 Edge Type。

例如：

```json
{
  "original_name": "ATTEMPTS_TO_REPAIR",
  "operation": "REVISE",
  "revised_edge_type": {
    "name": "ATTEMPTS_TO_REPAIR",
    "definition": "A subsequent agent action attempts to resolve a problem or failure identified during an earlier execution step.",
    "source_description": "An earlier observed problem or execution failure.",
    "target_description": "A subsequent agent action intended to resolve the identified problem or failure."
  }
}
```

允许修改名称：

```json
{
  "original_name": "SUCCESSFUL_SETUP_ENABLES_SUBSEQUENT_USE",
  "operation": "REVISE",
  "revised_edge_type": {
    "name": "ENABLES_SUBSEQUENT_ACTION",
    "definition": "...",
    "source_description": "...",
    "target_description": "..."
  }
}
```

应用规则：

```text
Original Edge Type
       ↓
REVISE
       ↓
完整 Revised Edge Type
       ↓
替换 Registry 中原类型
```

---

# 九、MERGE

`MERGE` 表示当前类型与 Registry 中另一个类型表达相同的核心语义关系，应合并到目标类型。

例如：

```json
{
  "original_name": "VERIFIES_PRODUCED_OUTPUT",
  "operation": "MERGE",
  "merge_into": "VERIFIES_OUTCOME_OF_PREVIOUS_ACTION"
}
```

其含义：

```text
VERIFIES_PRODUCED_OUTPUT
             │
             ▼
MERGE INTO
             │
             ▼
VERIFIES_OUTCOME_OF_PREVIOUS_ACTION
```

最终 Registry 中保留目标类型。

如果目标类型本身也需要修改，则目标类型自己的 Revision 项使用 `REVISE`：

```json
[
  {
    "original_name": "VERIFIES_PRODUCED_OUTPUT",
    "operation": "MERGE",
    "merge_into": "VERIFIES_OUTCOME_OF_PREVIOUS_ACTION"
  },
  {
    "original_name": "VERIFIES_OUTCOME_OF_PREVIOUS_ACTION",
    "operation": "REVISE",
    "revised_edge_type": {
      "name": "VERIFIES_PREVIOUS_OUTCOME",
      "definition": "...",
      "source_description": "...",
      "target_description": "..."
    }
  }
]
```

这样：

```text
VERIFIES_PRODUCED_OUTPUT
        ┐
        ├──→ VERIFIES_PREVIOUS_OUTCOME
        │
VERIFIES_OUTCOME_OF_PREVIOUS_ACTION
        ┘
```

为了使 Revision Plan 具有明确的执行顺序，`MERGE` 的 `merge_into` 指向一个操作为：

```text
KEEP
或
REVISE
```

的原始 Registry 类型。

这样所有 Merge 都有一个稳定的最终目标。

# 十一、Registry Revision System Prompt

创建：

```text
build_edges/prompts/registry_revision/system.txt
```

内容：

```text
You are an expert in maintaining a semantic edge type registry for agent execution trajectories.

Every fixed number of context windows, a human reviewer provides natural-language feedback about the current edge type registry.

Your task is to apply the human feedback consistently to the complete current registry.

For every edge type in the current registry, assign exactly one revision operation:

KEEP
DELETE
REVISE
MERGE

## Operation Definitions

KEEP:
Preserve the edge type exactly as it currently appears in the registry.

DELETE:
Remove the edge type from the registry when the human feedback indicates that the semantic relationship should no longer remain as an independent type.

REVISE:
Preserve the underlying semantic relationship while revising its name, definition, source_description, and/or target_description.

For REVISE, return the complete revised edge type with exactly four fields:

name
definition
source_description
target_description

MERGE:
Merge the current edge type into another edge type already present in the current registry when they should represent one semantic relationship.

For MERGE, specify the target type using merge_into.

The merge_into value must refer to the original name of another edge type in the supplied registry whose operation is KEEP or REVISE.

## Revision Rules

1. Review every edge type in the supplied registry.

2. Assign exactly one operation to every input edge type.

3. Apply the human feedback consistently across the complete registry.

4. Use the supplied granularity rules and positive and negative examples to interpret the human feedback.

5. Evaluate semantic meaning, applicability conditions, source role, target role, and relationship direction.

6. Preserve distinct semantic relationships when their meanings, applicability conditions, or endpoint roles are meaningfully different.

7. Use REVISE when an existing relationship remains useful but its current abstraction, name, definition, or endpoint descriptions should be improved.

8. Use MERGE when multiple registry types should represent one underlying semantic relationship.

9. Use DELETE when the human feedback indicates that a type should no longer be represented independently and no merge target is appropriate.

10. Use KEEP when the current edge type already satisfies the human feedback and granularity criteria.

11. When a MERGE target needs a broader or clearer definition, assign REVISE to the target type.

12. Maintain a consistent relationship direction across definition, source_description, and target_description.

13. Revised edge type names use uppercase underscore-separated naming.

## Output Schema

Return valid JSON using exactly this structure:

{
  "revisions": [
    {
      "original_name": "...",
      "operation": "KEEP"
    },
    {
      "original_name": "...",
      "operation": "DELETE"
    },
    {
      "original_name": "...",
      "operation": "REVISE",
      "revised_edge_type": {
        "name": "...",
        "definition": "...",
        "source_description": "...",
        "target_description": "..."
      }
    },
    {
      "original_name": "...",
      "operation": "MERGE",
      "merge_into": "..."
    }
  ]
}

Return only the JSON object.
```

# 十四、`registry_revision.py`

新增：

```text
build_edges/registry_revision.py
```

提供：

```python
def run_registry_revision(
    human_feedback: str,
    existing_registry: list[dict],
    llm_client,
    prompt_loader,
) -> dict:
    """
    根据 Human Feedback 对完整 Registry 生成 Revision Plan。

    返回：
    {
        "revisions": [...]
    }
    """
```

核心流程：

```python
def run_registry_revision(
    human_feedback,
    existing_registry,
    llm_client,
    prompt_loader,
):
    system_prompt = (
        prompt_loader.load_registry_revision_system()
    )

    granularity_examples = (
        prompt_loader.load_granularity_examples()
    )

    user_template = (
        prompt_loader.load_registry_revision_user()
    )

    system_message = (
        system_prompt
        + "\n\n"
        + granularity_examples
    )

    user_message = render_template(
        user_template,
        human_feedback=human_feedback,
        existing_registry=json.dumps(
            existing_registry,
            ensure_ascii=False,
            indent=2,
        ),
    )

    response = llm_client.generate(
        system=system_message,
        user=user_message,
    )

    revision_plan = parse_json_response(
        response
    )

    validate_registry_revision_plan(
        revision_plan,
        existing_registry,
    )

    return revision_plan
```

调用记录沿用当前 LLM 请求记录机制。

# 十五、Revision Plan Validator

在 `validator.py` 中增加：

```python
validate_registry_revision_plan(
    revision_plan,
    existing_registry,
)
```

分为五类验证。

## 15.1 顶层 Schema

检查：

```text
revisions
```

为数组。

每个 Revision Entry 包含：

```text
original_name
operation
```

其中：

```text
operation ∈ {
    KEEP,
    DELETE,
    REVISE,
    MERGE
}
```

---

## 15.2 完整覆盖

设 Registry 中原始名称集合：

$$
N_R
$$

Revision Plan 中 `original_name` 集合：

$$
N_P
$$

要求：

$$
N_R=N_P
$$

同时每个 `original_name` 恰好出现一次。

例如 Registry 有：

```text
A
B
C
D
```

Revision Plan 也必须覆盖：

```text
A
B
C
D
```

---

## 15.3 REVISE 验证

对于：

```text
operation = REVISE
```

检查存在：

```text
revised_edge_type
```

并满足原有四字段 Schema：

```text
name
definition
source_description
target_description
```

全部为非空字符串。

---

## 15.4 MERGE 验证

对于：

```text
operation = MERGE
```

检查：

```text
merge_into
```

对应当前输入 Registry 中另一个真实存在的 `original_name`。

同时检查 Merge Target 对应的 operation 为：

```text
KEEP
或
REVISE
```

例如：

```text
A → MERGE into B
B → REVISE
```

属于有效结构。

---

## 15.5 最终名称唯一性

根据完整 Revision Plan 计算 Revision 后保留下来的类型名称，并检查最终名称唯一。

例如：

```text
A → REVISE → NEW_NAME
B → KEEP → B
C → MERGE → B
```

最终名称：

```text
NEW_NAME
B
```

应保持唯一。

---

# 十六、Revision Plan 应用算法

在 `registry.py` 增加：

```python
def apply_registry_revision(
    existing_registry: list[dict],
    revision_plan: dict,
) -> list[dict]:
```

建议采用两阶段应用，确保与 JSON 顺序无关。

## 16.1 建立操作索引

```python
revision_by_name = {
    item["original_name"]: item
    for item in revision_plan["revisions"]
}
```

同时：

```python
registry_by_name = {
    edge["name"]: edge
    for edge in existing_registry
}
```

## 16.2 第一阶段：构造所有保留目标

遍历原始 Registry：

### KEEP

加入原始 Edge Type：

```python
new_registry.append(
    copy.deepcopy(original_edge)
)
```

### REVISE

加入：

```python
new_registry.append(
    revision["revised_edge_type"]
)
```

### DELETE

不加入新的 Registry。

### MERGE

当前类型本身不加入新的 Registry。其语义归入 `merge_into` 指定的目标类型。

由于 Merge Target 本身使用 `KEEP` 或 `REVISE`，目标会由自己的 Revision Entry 自动进入新 Registry。

因此整个应用算法无需依赖模型输出数组的顺序。

# 十七、Revision 后 Registry 校验

`apply_registry_revision()` 完成后，再执行现有 Registry Validator：

```python
validate_registry(revised_registry)
```

至少检查：

1. 每个类型均为四字段 Schema。
2. 名称符合格式。
3. 名称唯一。
4. 所有字符串非空。
5. Revision Plan 中的 KEEP 类型在新 Registry 中保持原始四字段内容。
6. REVISE 类型使用返回的新四字段对象。
7. DELETE 类型不存在于新 Registry。
8. MERGE Source 不再作为独立类型存在。
9. MERGE Target 对应的 KEEP 或 REVISE 结果存在于新 Registry。

验证成功后再替换当前 Registry。

```text
VERIFIES_PRODUCED_OUTPUT
  → VERIFIES_OUTCOME_OF_PREVIOUS_ACTION

【DELETE】

REVEALS_MISSING_PREREQUISITE
```

KEEP 类型无需逐个在终端打印，数量统计即可。

# 二十一、`handle_registry_feedback`

实现：

```python
def handle_registry_feedback(
    batch_index,
    registry,
    batch_result,
    prompt_manager,
    llm_client,
    output_dir,
):
    # 1. 展示本批结果
    print_registry_feedback_summary(...)

    # 2. 读取自然语言 Feedback
    human_feedback = read_human_feedback()

    # 3. 保存原始 Feedback
    save_human_feedback(
        batch_index,
        human_feedback,
    )

    # 4. 调用 Revision LLM
    revision_plan = run_registry_revision(
        human_feedback=human_feedback,
        existing_registry=registry,
        llm_client=llm_client,
        prompt_loader=prompt_manager,
    )

    # 5. 应用 Revision Plan
    revised_registry = apply_registry_revision(
        existing_registry=registry,
        revision_plan=revision_plan,
    )

    # 6. 验证最终 Registry
    validate_registry(
        revised_registry
    )

    # 7. 保存 Revision 全部记录
    save_registry_revision_result(
        batch_index=batch_index,
        registry_before=registry,
        revision_plan=revision_plan,
        registry_after=revised_registry,
    )

    # 8. 更新正式 Registry
    save_registry(
        revised_registry,
        output_dir,
    )

    # 9. 中文输出修改摘要
    print_registry_revision_summary(
        registry_before=registry,
        revision_plan=revision_plan,
        registry_after=revised_registry,
    )

    return {
        "registry": revised_registry,
        "prompt_version": (
            prompt_manager.current_version
        ),
    }
```

在 `registry_feedback` 模式中，Prompt 版本保持当前版本。

# 二十二、主循环修改

原来的 Batch 边界逻辑：

```python
if batch_finished:
    save_batch_review_packet(...)

    feedback_result = handle_batch_feedback(
        feedback_mode=config["feedback_mode"],
        batch_index=batch_index,
        registry=registry,
        batch_result=batch_result,
        prompt_manager=prompt_manager,
        llm_client=llm_client,
        output_dir=output_dir,
    )

    registry = feedback_result["registry"]

    prompt_manager.activate_version(
        feedback_result["prompt_version"]
    )

    batch_index += 1
```

因此：

### `manual_prompt`

```text
用户手动修改 Prompt
→ Registry 保持不变
→ Prompt 可能更新
```

### `registry_feedback`

```text
用户自然语言 Feedback
→ Registry 自动 Revision
→ Prompt 保持不变
```

两种模式共享同一个主循环。

# 二十三、最后一批的反馈规则

保持与现有人工反馈逻辑一致：**每完成一个完整的 10-Window Batch 执行 Human Feedback。**

例如：

```text
共有 27 个 Window
```

执行：

```text
Window 1–10
→ Registry Feedback

Window 11–20
→ Registry Feedback

Window 21–27
→ 保存最终 Batch 结果
→ 完成
```

最后不足 10 个 Window 的部分直接作为最终结果保存。

如果总 Window 数恰好为 30：

```text
1–10 → Feedback
11–20 → Feedback
21–30 → 任务结束
```

最后一个 Batch 已无后续 Window，因此保存最终 Registry 和 Batch 结果后结束。

# 二十四、空 Feedback 处理

用户可以提交空 Feedback。

例如直接：

```text
> END
```

此时程序将其解释为本批无需修改 Registry：

```text
【Registry Feedback】

本轮未输入修改意见。
当前 Registry 保持不变。

开始处理下一批 Window...
```

保存：

```text
human_feedback.txt
```

为空文本，并生成批次元数据：

```json
{
  "feedback_applied": false
}
```

该情况下可以直接跳过 Registry Revision LLM 调用。

# 二十五、LLM Revision 调用失败处理

Revision 调用沿用：

```yaml
max_llm_retries: 3
```

终端：

```text
【Registry Revision 失败】

原因：Revision Plan 未覆盖全部 Edge Types。

正在进行第 2 / 3 次重试...
```

重试使用相同：

```text
Human Feedback
Current Registry
Revision Prompt
Granularity Examples
```

达到最大重试次数后：

```text
【Registry Revision 未完成】

当前 Registry 已保持原状态。
Revision 失败记录已保存：

  output/batches/batch_0001/registry_revision_error.json
```

将当前状态标记为 `failed`，支持现有 `--resume` 机制继续 Registry Revision。
